# PantryFlow 產品決策紀錄｜2026-08-20

本文件記錄 2026-08-20 已確認的產品決策。若舊版畫面或說明與本文件衝突，以本文件的最新決策為準；若新需求衝突，開發前先提出確認。

## 1. 首頁正式版

首頁固定依序呈現：

1. 今日重點：缺貨風險、即期提醒、待確認異常的簡潔摘要。
2. 每日作業：盤點、進貨、廢棄、效期檢查、其他作業。
3. 今日建議：選用元件，只顯示 1～2 個有用建議。
4. 商家留言板：選用元件，放在首頁後段。

首頁不是工作流程頁，不使用「現在先做」、不強制把盤點放成第一個大型任務，也不新增大型 Dashboard 或 KPI。

## 2. 每頁簡潔有力

一個畫面只回答一個問題；結論與必要入口優先，正常資訊弱化，詳細資料按需展開。功能流程內可以逐步引導，但首頁不做成 wizard。

## 3. 日期使用實際日期與時間

主要資訊必須顯示實際日期或時間，例如 `2026/08/20`、`2026/08/20 10:25`。今天、明天、已逾期可以作為輔助狀態，但不可單獨以「0 天、1 天前、2 天後」取代實際日期。

## 4. 盤點流程

盤點流程固定為：盤點區域 → 區域數量輸入 → 全部區域完成 → 差異整理 → 回覆原因 → 完成。第一線盲盤、只輸入數字、單位唯讀、自動保存、不逐項確認。第一次實盤與後續更正都保留為不可覆蓋的事件紀錄。

## 5. 效期巡檢

效期巡檢與盤點共用同一套區域資料。只列今天要看與容易漏掉的位置；正常品項不要求逐項勾選。公版風險重點可先使用，店家依現場盲區漸進新增。效期原始紀錄不可直接延後或覆蓋。

## 6. 進貨第一線只上傳照片

第一線只負責拍照或從相簿選擇多張貨單照片，確認清楚後一次上傳。現場不核 AI 辨識、編碼、金額、稅額或含稅／未稅；上傳成功即可繼續工作。

## 7. 收貨待核對

後續流程為：收貨待核對 → 編碼確認／建立 → 明細核對 → 供應商對帳／成果輸出。角色由權限決定，不寫死為後勤。AI 原始辨識、原始照片與人工修正分開保存。

## 8. 編碼為可選模組

已有 ERP 的企業沿用 ERP 料號或 Mapping；沒有 ERP 的餐廳可在核對流程建立統一物料編碼。換供應商、規格、包裝或名稱不等於建立新商品，Product ID 必須維持一致。

## 9. 未稅、稅額、含稅分離

進貨資料分開保存未稅小計、稅額與含稅總額。價格與稅務欄位由系統或核對角色處理，不回頭要求第一線判斷。

## 10. Excel 匯出可重新產生

第一版只提供 Excel 匯出，不提供 Google Sheet 同步。Excel 是成果輸出，不是 PantryFlow 的唯一資料來源；檔案跑版、損壞或被人工修改都不得影響內部資料，使用者必須能重新匯出。

## 11. 原始資料不可覆蓋

原始貨單照片、AI 原始辨識、第一次實盤、效期批次與其他現場紀錄不可被後續操作覆蓋。人工修正、複盤與更正都另存事件，保留操作者與時間。

## 12. 數位化不能等於重複作業

PantryFlow 不改企業既有制度，而是補制度與現場之間的落差。同一件事只輸入一次，後續整理、計算與追蹤由系統接續；現場完成的是收貨作業，不是會計作業。

## 13. BeApe Pilot v0.1 雲端決策

Pilot 前端維持 static HTML、CSS、vanilla JavaScript 與 GitHub Pages，不更換框架。正式資料來源改為 Supabase Auth、Database 與私有 Storage，`localStorage` 僅供暫存或 fallback。

本輪只有盤點與進貨／收貨後勤是正式 Pilot 流程；其他大型模組不擴充。使用者以個人帳號登入同一 BeApe organization，角色為 ADMIN、SUPERVISOR、STAFF。

盤點第一次實盤、複盤與更正分開追加；收貨原圖、AI 原值、人工修正與正式收貨分開保存。正式收貨以單一資料庫交易完成，失敗時不得留下半套正式資料。Excel 可以反覆由 Supabase 原始資料產生，匯出檔被修改或損壞不得回寫影響 PantryFlow。
